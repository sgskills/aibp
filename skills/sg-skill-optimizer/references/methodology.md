# SG Skill Optimizer 方法论

> 本文解释本 Skill 自己采用的判断框架。它不是安装依赖，也不要求用户同时拥有其他优化 Skill。

## 1. 证据分层

任何质量结论必须注明证据层级：

1. **静态证据**：frontmatter、目录、契约、检查点、失败分支和资源引用；
2. **可执行证据**：fixture、机器断言、runner 退出码和本轮通过率；
3. **真实表现证据**：同一测试任务下，启用 Skill 与通用基线的输出对照。

只有静态证据时不能声称“真实效果满分”。书面 Golden Set 只能记为 `SPEC_ONLY`；有 runner 但未运行记为 `EXECUTABLE`；本轮机器断言全部通过才记为 `VERIFIED`。

## 2. 适用项分数与覆盖率

`N/A` 表示检查在当前场景不适用，例如独立发行时没有 Skills 根目录可供冲突审计。它不扣适用项分数，也不能算通过。

报告同时展示：

- **适用项静态分**：只衡量本轮可评分的静态检查；
- **证据覆盖率**：全部检查权重中，本轮实际有证据的比例；
- **置信度**：综合未运行、`MANUAL`、`N/A` 和回归状态。

因此 `100 / PARTIAL / 覆盖 97%` 的含义是“已检查的静态项全部通过，但证据仍不完整”，不是总体质量满分。

## 3. 优化顺序

按风险和收益排序：

1. `P0`：坏 frontmatter、不可逆操作、敏感信息、未授权代码执行、虚假评测；
2. `P1`：触发边界、输入输出契约、失败恢复、输出稳定、真实回归；
3. `P2`：目录分层、资源索引、版本记录和表达精简。

每条修改必须绑定证据和验收方式。没有验收方式的“优化建议”不得进入实施队列。

## 4. 决策显性化

把“看情况”“灵活处理”改写为可观察条件：

```text
IF 条件 A → 动作 A
ELIF 条件 B → 动作 B
ELSE → 安全降级或提问
```

普通编号、章节中的数字、模板占位符不构成决策树证据。

## 5. 失败机制编码

失败处理使用三段式：

| 触发条件 | 首选处理 | 仍失败 |
|---|---|---|
| 可观察症状 | 最小风险修复 | 停止、降级、回滚或提问 |

必须覆盖与任务真实相关的文件、编码、权限、工具、网络、数据和子进程风险；不为纯假设堆砌兜底。

## 6. 安全执行

- 默认只读，修改前显式确认并建立回滚点；
- 目标目录中的脚本属于目标代码，不能因文件名叫 `run_eval.py` 就默认可信；
- 执行目标代码前检查内容、取得确认，并优先使用沙箱；
- 没有沙箱且目标不可信时不执行；
- 子进程必须有超时，输出必须验证结构和内部一致性；
- runner 摘要不一致时，可信 `passRate` 必须清空；自报值只能放入明确标记为不可信的 `reportedPassRate`；
- 环境扫描排除测试素材、依赖、缓存、版本控制和虚拟环境目录。

## 7. 可执行回归设计

一个有效案例至少包含：

- 固定输入目录；
- 机器可读的预期结果；
- 明确的通过/失败断言；
- 非零失败退出码；
- 能复现的运行命令。

最低覆盖：健康对照、坏 frontmatter、安全红线、只有书面 Golden Set、缺输出契约、触发冲突或 N/A 边界。

## 8. 迭代闭环

每次发现误报、漏报或危险行为：

1. 先添加能复现问题的失败测试；
2. 修改最小必要逻辑；
3. 重跑完整回归；
4. 更新变更记录和回滚说明；
5. 真实表现没有对照证据时，明确保留人工验证项。
