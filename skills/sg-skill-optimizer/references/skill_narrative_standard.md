# Skill 叙事与路由规范

适用于**新建或改造 Skill**时的 `description` 与正文开场。目的不是写得更有气势，而是让模型和用户能在最短上下文内判断：它是什么、何时该用、交付什么、何时不该用。

## 1. Frontmatter：一句话定位在最前

`description` 的第一句只写“任务类别 + 核心对象 + 结果”，不要先罗列工具、步骤、表格、平台或所有子能力。

```yaml
description: |
  [一句话定位]。 [补充适用条件与结果]。
  触发方式：[明确表达、典型说法或命令]。
  [English task equivalent].
  Trigger: "[English trigger]"
```

检查：

- 一句话定位能脱离正文被人复述；
- 触发词在前 1–2 句出现；
- 同时写清适用与不适用边界；
- 双语、触发方式是可选增强，不得挤掉核心定位；
- 不用“专业、全面、智能、强大”等空泛形容词开头。

## 2. 正文开场：角色、任务、交付、边界、前提

标题之后用 3–6 句建立行动契约，顺序如下：

1. **角色**：你在此任务中负责什么判断或工作；
2. **任务**：把用户的什么输入转化为什么结果；
3. **交付**：最终交付物是什么，而不只是过程；
4. **边界**：明确不替用户做什么，或不解决什么相邻问题；
5. **前提**：缺少什么信息时先澄清、降级或停止。

模板：

```md
# [Skill 名称]： [一句话定位]

你负责 [角色/判断]。你的任务是把 [输入] 转化为 [交付]。

你不负责 [相邻但不同的任务]；[用户/系统] 负责 [保留给对方的决策]。

前提：若 [必要条件] 不满足，先 [澄清/降级/停止]，不要假装已完成。
```

只有确实会改变决策的机制，才可追加一条“核心判断”或“常见误区”。它必须能导向后续动作，不能只是口号。

## 3. 结尾：安全的下一步导航

当用户不知道下一步时，Skill 可以说明**本 Skill 内的下一步**，或指出请求已超出当前边界。导航必须：

- 基于已声明的输入、输出和边界；
- 不擅自调用、安装或假定存在其他 Skill；
- 不得假定安装其他 Skill，也不得把其他 Skill 当作默认前置条件；
- 不虚构命令、路由名或外部工具；
- 若没有确定的下一步，明确写“需要用户选择目标或提供缺失输入”。

推荐收口：

> 如果下一步不确定，先确认你要达成的交付和可用输入；信息不足时保留当前结论，列出待补项，而不是替用户选择无关工具。

## 4. 反例

- 将所有能力、工具、指标和平台塞进第一句；
- 正文开头只写身份或口号，没有交付与边界；
- 把相邻 Skill 名称、命令或品牌当成默认出口；
- 用“按情况处理”代替必要前提和失败分支。
