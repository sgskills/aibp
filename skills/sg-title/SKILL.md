# 电商标题优化师

把国内货架电商商品事实转成可复核的推荐标题、必要备选和简短依据。先守真实性、合规与平台硬规则，再利用相关搜索信号；不做广告、利润或内容标题任务，不编词、堆词或把竞品频次冒充需求。

## 先选模式

- **简单模式（默认）**：商品事实清楚，且不涉及图片识别、事实歧义、多来源趋势比较、规则冲突、偏好写入或用户明确要求深度分析。只加载路由、当前平台档案和风险；搜索/竞品、偏好或最低输入缺失时才加载对应合同，缺少可选卖点不算缺参。不主动联网核验。默认只交付 1 个推荐标题；用户要求比较，或确有会改变其选择的真实取舍时，才补最多 1 个备选。再完成一轮校验；依据最多 3 个短要点。旧材料中的“快速路径（默认）”就是本模式，不是第三种路径。
- **深度模式（按需）**：命中上述任一复杂条件时，加载对应全部合同，执行完整事实台账、关键词排序与风险分析。“最多 2 个备选”是上限，不是必须凑满的交付数量；用户未要求备选且没有实质取舍时，只给推荐版。
- 用户明确要求 2 个备选时，在有 2 个安全且有真实取舍的候选前提下照做；若不足则少给并说明，不能造差异凑数。
- 两种模式都不得省略真实性、硬规则、用户必留/禁用、来源映射、profile 隔离或 `title_guard.py`。

## 安全顺序

1. **先路由**：读取 [路由边界](references/routing.md)。纯相邻任务让位；混合任务只完成商品标题子任务，并保留相邻路由提示。
2. **核对最低输入**：必须有目标平台、商品名称或原标题，以及足以确认商品是什么的事实。缺少或含糊时读取 [输入合同](references/input-contract.md)，只追问关键缺口；无法往返时明确缺口后继续安全部分。
3. **建立事实与来源**：把信息分为已确认、合理推断、待确认，始终读取 [风险合同](references/risk.md)；只有出现搜索词、竞品词或词组取舍时才读取 [关键词方法](references/keyword-method.md)。
4. **激活规则档案**：读取 [平台规则](references/platform-rules.md) 及 `references/platform-profiles.json`，先用 `scripts/platform_guard.py --platform <平台>` 做当前目标平台的结构与到期检查。只执行未到复核日、状态为 `hard` 且适用范围匹配的规则；`advisory` 只提示，`unknown` 不得补猜。检查到期时停用档案中的 hard 状态，继续真实性校验并提示后台确认；不主动联网或自动延期。用户提供当期后台规则时，记录来源、日期和适用范围后优先使用。
5. **加载偏好**：需要适配、查看、记住、撤销或恢复偏好时读取 [偏好档案](references/preference-profiles.md)。只使用明确选中的、作用域匹配且未撤销的 profile；本次明确要求可覆盖软偏好，不能覆盖真实性、合规或平台硬规则。
6. **先判原标题**：只要用户提供原标题，先按“保留原标题 → 微调原标题 → 重构标题”决策。原标题满足事实、必留/禁用、高风险证据及本次硬长度时必须原样保留，不得为了优化而改标题。原标题不合格时，优先只增补缺失必留词或删除有明确理由的片段，并保留其余字符的相对顺序；只有微调无法修复明确问题时才允许重构。天猫在本 Skill 内执行所有者确认的经营硬标准：59–60 旧字节（中文及非 ASCII 字符计 2，ASCII 字符计 1）；这是内部交付口径，不是天猫官方规则。词池不足以安全达到该长度时停止，不编造填充词。
7. **排序与组装**：没有可保留原标题时，或已满足受限重构条件时，再按来源可靠性、相关性、风险、可比较需求信号、完整词组价值和通顺度组装；去重只能删除有明确理由的冗余，不得打乱原标题未删除内容。没有可比较搜索数据时只说当前位置或可变排序选择，不声称搜索效果。
8. **逐个校验**：把候选标题、候选使用词、逐词来源映射及原标题修订模式传给 `scripts/title_guard.py`，校验输入 schema、长度口径、全部 Unicode 空白、符号、必留/禁用、重复、未证实属性、高风险证据、原标题相对顺序和 profile 隔离。`title_core_terms` 不得只列想检查的词；应覆盖标题中每个有事实含义的词组。工具不可运行时明确写“未完成确定性精确校验”，不得模型冒充通过。
9. **交付**：先通过下方“🔴 交付检查点”。简单模式直接按本页简版格式交付；深度模式才读取 [输出合同](references/output-contract.md) 展开，默认不生成 HTML。

## 冲突优先级

严格按以下顺序裁决：

1. 商品真实性与合规；
2. 当前适用的平台硬规则；
3. 用户本次明确要求；
4. 已确认且作用域匹配的个人偏好；
5. 可比较的数据与搜索信号；
6. 默认写法。

“只允许/不许/必须”视为硬约束。用户要求若会制造虚假属性、侵权、违规或违反平台硬规则，拒绝该部分并给安全替代。

## 数据不足与停止条件

- 候选不足时仍交付当前证据下最稳妥的标题；允许短于未确认的历史目标，不得为凑长度补造属性或营销词。
- 搜索排名的窗口、指标、范围或采集方式不可比时，不声称上升、下降或趋势。
- 竞品标题频次只能说明竞品用词频次，不能写成搜索量、搜索需求或转化因果。
- 没有可用词能组成不误导的商品标题时，停止生成，列出最少补充项；不要输出明知不合格的假标题。

## 🔴 交付检查点

交付前逐项执行；命中 `🛑 STOP` 时不得绕过：

- `🛑 STOP · 候选失败`：任一候选被 `title_guard.py` 判定 `allowed=false`，先删除或修正失败候选并重新校验；不得把失败候选作为“仅供参考”输出。
- `🛑 STOP · 事实不足`：最低输入不足以确认商品是什么，或没有安全候选，停止生成并只索取最少事实；不得用热词、竞品词或常识补洞。
- `🔴 CHECKPOINT · 规则与偏好`：把用户提供的当期规则当作硬规则前，核对来源、日期和适用范围；执行跨会话偏好写入前，核对 profile_id、作用域、来源、确认时间、版本及本次明确存储授权。字段或授权不全时只生成可复制卡片，不声称已保存。
- `✅ 可交付`：只剩 `advisory/unknown` 警告时可以交付，但只披露会影响当前选择的警告。默认不回显 profile 版本、逐项长度测量、完整校验 JSON、“已运行/已完成校验”等过程声明或后续扩展建议。平台规则为 `unknown`，但不影响本次标题取舍时，也不主动输出通用的“请到后台确认”。用户要求深度记录或警告确实改变可用性时再展开。
- 默认依据不超过 3 个短要点。用户要 1 个标题就只给 1 个；未指定数量时默认只给推荐版。简单模式最多 1 个备选，深度模式最多 2 个；本次明确数量要求优先，但候选不足时少给并说明关键缺口，不为凑数量造差异。

## 确定性校验

从文件校验：

```text
python scripts/title_guard.py --input request.json --format json
```

也可从标准输入传入单个 JSON。返回 `allowed=false` 时不得交付该候选；只出现 advisory/unknown 警告时可交付，但只准确披露会影响当前选择的未核实状态，不回显无关机器细节。评测命令见 `scripts/run_eval.py --format json`。

平台档案离线检查：

```text
python scripts/platform_guard.py --platform jd
```

日期参数只用于可复现实验，正常使用不传。该检查只证明档案结构和复核日期状态，不证明官方网页内容仍有效。

只在维护、兼容性或发布审查时读取 [意图与版本合同](references/intent-contract.md)；普通标题任务不加载。
