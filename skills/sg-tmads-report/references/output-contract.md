# 输出契约

## 对话优先

默认交付是对话中的完整 Markdown 诊断，不因为当前客户端能够写文件就自动生成 HTML。先给一屏内关键结论：

1. 能力等级与能否回答用户目标；
2. 最大数据质量/归因风险；
3. 整体周期的关键数据事实；
4. 最优先处理的计划或数据缺口；
5. 不可计算项和下一步。

若仍在追问阶段，对话先给审表结论与最多 5 问。无法等待或用户要求直接继续时，同一回复继续提供无假设标准报告。

完成诊断后最多主动询问一次：

> 是否需要我把这份诊断生成一份可筛选、可排序、方便保存和转发的离线 HTML 报告？

- 用户明确同意或一开始已经要求 HTML：可以生成；
- 用户不回答、拒绝或只要求解决问题：不生成 HTML，也不创建输出目录；
- 同一份诊断被拒绝后不重复询问；
- 无法写文件时保留完整 Markdown，并如实说明未创建文件。

## ReportModel v2.1

确定性证据、Agent 诊断与可选 HTML 使用同一个结构化模型：

```text
schema_version / checkpoint_status / calculation_mode / file_status
coverage / context / audit.dataset_inventory / audit.mapping_ledger / audit.attribution_registry
audit.budget_checks / audit.narrative_validation / assumptions
islands[overall / daily / campaigns / item_campaigns / not_computable / details]
executive_summary / summary_cards / insights / diagnoses / actions(ActionRecord v2) / questions / formulas
```

脚本只计算证据；`executive_summary`、`diagnoses` 与 `actions` 由 Agent 在完成审表、追问和计算后写入，渲染器不得自行编造。

例外（2026-08-06 起）：`summary_cards` 与 `insights` 由脚本从证据模型确定性聚合出默认版本（计划大类盈亏、新建亏损占比、成熟零成交、下期守则与对账钩子），保证任何 Runtime 即使只提供最小叙事也能产出完整的「执行摘要卡」与「经验沉淀与正循环」章节；Agent 基于证据写有判断力的版本时可整体覆盖这两个字段。脚本默认版只陈述本期数据支撑的模式，不写行业真理；守则必须标注「本期证据」或「待验证」。

`ActionRecord v2` 使用双层动作：`target_action` 表示最终方向，`allowed_action` 表示当前真正允许做的动作，兼容字段 `action_code` 必须等于 `allowed_action`。动作需带 `action_level`、对象身份、证据引用、约束、升级条件和复核合同；出价控制通过 `context.control_levers` 引用用户确认，关闭通过 `context.action_confirmations` 引用用户确认。旧 ActionRecord 仍可读取，但新生成报告必须使用 v2。

`coverage.sections` 对每个章节标记 `complete / not_applicable / not_computable / missing`：

- 数据本身不支持时使用 `not_applicable` 或 `not_computable` 并显示原因；
- 实现缺失或没有诊断叙事时使用 `missing`；
- 只有诊断与行动都存在，且没有实现缺失时，`report_status` 才能是 `full`；
- 诊断与行动还必须通过证据引用、对象维度、归因、预算和不可暂停约束门禁；`audit.narrative_validation.status=blocked` 时不得升级为 `full`；
- 缺少诊断或行动时只能输出“数据分析附件”，不得称“完整诊断报告”。

报告顶层同时披露：

- `checkpoint_status=awaiting_user|bypassed_by_user|no_roundtrip|answered`；
- `calculation_mode=script|manual|not_computable`；
- `file_status=created|not_created`。

脚本模式可通过 `--checkpoint-status` 写入真实交互状态；省略时，有待答问题标为 `awaiting_user`，没有待答问题标为 `answered`。没有实际运行脚本、读取 XLSX 或创建文件时，不得给出相反状态。`file_status=created` 只表示当前命令实际请求了可写输出；写入失败时必须报错，不能在对话中声称文件已创建。

## 完整诊断结构

1. 报告范围、文件与 Sheet 盘点；
2. 数据岛、字段映射和能力分级；
3. 归因来源台账、预算约束检查、叙事安全门禁；
4. 未确认口径、追问与回答；
5. 整体周期；
6. 每日趋势；
7. 计划周期汇总及计划日期缺口/隔离日期；
8. 商品/计划组合（字段支持时）；
9. 诊断与动作清单；
10. 不可计算项、风险与补数清单；
11. 计划 × 日期完整附录；
12. 公式、假设和生成时间。

即使界面默认折叠附录或只展示筛选结果，模型中也必须保留全部计划和全部日期明细。

完整行动队列同样不得只保留 Top N：每个可识别计划 ID 至少一条独立 ActionRecord。首屏只挑最高优先级计划，筛选后的计数、行动卡计数与队列总数必须来自同一 `actions` 数组并能够对账。

## 可选 HTML

只有用户明确需要文件时才生成单个离线 `.html`：

- CSS、JavaScript 全部内联；
- 不引用外部图片、字体、CDN、脚本或样式；
- 行动驾驶舱先于 KPI 展示，并把“目标动作”与“当前允许动作”并排显示；
- 行动队列可按当前允许级别、目标动作、数据岛、商品、受保护状态、归因状态、日期异常和计划文本筛选；至少包含增加预算、减少预算、增加出价、降低出价、预算重分配、保持、暂停和关闭候选；
- 数据岛用可键盘操作的标签页切换；计划表和日期明细可文本筛选，可按列排序；
- 行动筛选卡和表格仅用于浏览报告，不显示可误解为代操作后台的执行按钮；
- 大量计划仍保留全部行；
- 所有用户文本、字段名和脱敏 JSON 文本先做 HTML 转义；
- 内联脚本不拼接或执行用户文本，不使用 `innerHTML` 注入用户值；
- 显示“商品毛利口径推广贡献盈亏”，不得写“净利润”；
- 对不可计算值显示原因，不把 `null` 渲染为 0。
- 正文先展示执行摘要、诊断和行动；完整明细默认折叠，避免用原始表格淹没决策信息。

默认不包含未知列完整原始值。用户明确要求并使用 `--include-raw` 时，只能显示经过脱敏的原始行，并提示自动脱敏并非完整隐私审计。

### 安全写入

- 用户没有指定保存路径时，使用新的时间戳或运行 ID 子目录；
- 用户指定路径时尊重该路径；
- 默认拒绝覆盖已有文件；用户明确确认覆盖后才使用 `--force`；
- 输入文件与任何输出文件同路径、JSON 与 HTML 输出同路径始终拒绝，`--force` 不能绕过；
- 先完成分析与渲染，再使用同目录临时文件和原子替换；
- 写入失败时不宣称成功，保留对话中的完整 Markdown。

## 数字呈现

- 金额和计数保留原始精度用于计算；展示时再格式化。
- 比率明确单位；ROI 与百分率不要混写。
- 任何汇总旁边均可追溯到总分子、总分母。
- 情景估算标签只修饰推广贡献盈亏与保本 PPC，并列出毛利率、退款金额率和适用范围。
- 数据来源未知、归因未知、字段歧义分别显示，不用一个笼统“数据可能不准”代替。

## 呈现层契约（v3，2026-08-06 定稿）

面向普通运营读者：重点必须用视觉层级直接给出来，不让用户从纯文字里自己找重点。以下规则与审计纪律同级，渲染器必须逐项满足。

### 文件与标题

- 报告标题：《{平台}推广诊断报告》，平台经 `--platform` 传入、默认天猫（如抖音、京东）；诊断与行动缺失时为《{平台}推广数据分析附件》。
- HTML 文件名强制规范：《{店铺}店铺{平台}推广诊断报告-YYMMDD》（YYMMDD 为诊断日期）；店铺名经 `--store-name` 传入，缺省为“未命名店铺”；文件名剔除非法字符。即使用户给了其他文件名，也按规范名落盘并提示。
- 副标题必须包含：店铺、平台、诊断时间（YYYY-MM-DD HH:mm）、诊断人（sg-tmads-report 及版本）、数据周期，随后才是审表等级等技术信息。

### 三分钟看完版（报告第一节）

- 先给决策锚点条：情景保本 ROI（假设齐全时）及其含义；无假设时明说不做盈亏判断。
- 再给全店汇总大卡：总花费（各岛真实消耗相加）、报表归因成交合计、全店 ROI、情景盈亏合计；成交/ROI/盈亏为分岛之和，归因窗口未确认互斥时必须紧跟口径警示“仅供量级参考，决策以分岛为准”，花费可直接相加不适用此警示。
- 然后才是分岛总账表与“最该动手的一件事”（由 campaigns 实算，不手填）。

### 行动驾驶舱与队列

- 计划按证据成熟度分梯队：P0 成熟零成交 / P1 净亏 / P2 贴近保本 / P3 加码候选 / 保持健康 / 小样本观察；梯队规则与阈值（如投放天数、花费下限、保本线倍数）必须在卡片上写明，标为视图规则而非行业结论。
- 梯队总览卡可点击并联动行动队列筛选；给出 P0+P1 可释放预算合计（事实数，不承诺增量）。
- 行动队列默认排序与重点关注卡同一规则：需调整的计划优先（减亏/暂停/重分配候选按亏损额降序 → 加码候选按盈利额降序），其余按花费降序，逐计划全量覆盖，避免亏损计划被高花费维持计划埋掉；展示“去后台操作前 3 问”提醒条。
- 重点关注卡片区（原“需要变化的计划”）标题固定为「重点关注的计划」，排序规则：减亏/暂停/重分配候选最前（按亏损额降序，止损收益是确定的）→ 加码候选（按盈利额降序，收益待验证）→ 其他按花费降序；不凭主观“重要度”排序。
- 数据岛展示顺序：按岛内亏损计划总亏损额升序（亏损最集中的岛排最前），无亏损计划的岛按岛盈亏升序排后，无盈亏数据时按花费降序；该顺序对三分钟版总账、分岛章节、每日趋势一致生效。
- 计划显示名一律以证据模型中的计划名称为准（驾驶舱卡、行动队列、诊断卡同口径）；叙事 JSON 的 `object` 文本与 `object_id` 仅作回退，禁止把裸 ID 当主显示名。
- 每个计划同时显示目标动作与当前允许动作；二者不同时必须给升级条件。

### 低价值信息黑名单（默认不呈现）

- 证据引用机器串（dataset_id#object 形式）不进入正文卡片；保留在结构化 JSON 供追溯。
- 全空列（如商品缺失、变化幅度待确认）整列隐藏，不用“未提供/待确认”填满表格。
- 全部为“无”的不可计算项、台账类内容（字段映射、归因来源、预算约束、叙事门禁）默认折叠，不进首屏。
- “保持并观察+阻断说明”类维持现状的说明文字不进最高优先级区；最高优先级只放需要变化的对象。

### 表格规范

- 计划周期汇总列序：计划→花费→成交→ROI→CPC→CVR→贡献盈亏→盈亏灯→日期覆盖（开始/结束/缺口/隔离）置表尾；按花费降序；亏损行整行淡红标识；盈亏用灯+文字（盈利/亏损），不用正负号让用户自己判断。
- 计数类字段（展现、点击、订单、买家、天数、行数）只显示整数，禁止小数点。
- 每日趋势在口径允许时给出当日情景盈亏与盈亏灯；计划 × 日期附录同样遵守计数整数化。

### 收尾：经验沉淀与正循环

- 收尾不复述摘要，必须包含三节：① 表现好的计划的共同点（按名称模式/投放时长/岛聚合，数字实算）；② 出问题的计划的共同点（如同为“测款”类亏损）；③ 下次再建计划的守则（每条标注“本期证据”或“待验证”，禁止写成行业真理）。
- 有历史对账数据时给出复核钩子（上期动作是否执行、效果如何）。

### 页脚

- 固定包含：生成时间、“单文件离线报告”、Skill 地址可点击链接 `<a href="https://github.com/sgskills/aibp">github.com/sgskills/aibp</a>`（新窗口打开，`rel="noopener"`）；链接以外的页脚文本照常转义。
